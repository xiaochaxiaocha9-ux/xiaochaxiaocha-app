# 可转发给 Muse / Rei 的修复提示词

请将以下规则用于后续向同一私人听读卡库发布资料，保持原有教学、科目授权、知识卡ID及复习记录不变。

先读取App仓库的`docs/CONTENT_PROTOCOL.md`。本次四个问题统一如下：

- `learning_state`存在时必须非空，JavaScript `text.length`不超过160；Python按UTF-16计数，常见emoji占2。它只写简短状态，长解释放`source_note`。不要为绕过错误静默截断，或把来源状态改成“掌握”。
- `reading_hash`校验Markdown原始字节；`audio_hash`校验MP3。`content_hash`是记录版本令牌，不能用来校验正文。旧POL/ENV的两种哈希不同是正常设计，禁止批量替换或修复历史哈希。以后修改任何发布字段都更新版本令牌。
- `source_node_id`在手机端可选，现有英语/数学非子卡可继续不填，不临时猜造父级。填写时只能等于自身ID或`-K01`形式子卡的父级。ID按科目隔离，修订号不能回退，纯排版不升`learning_revision`。
- 优先只生成本批次差量JSON，由统一`publisher.ps1 submit`处理音频与提交；本机启用科目由现有配置控制，不自行改配置。没有MP3二进制上传通道就交付听觉文本，不把二进制当UTF-8文本上传。

如果继续独立经API发布，必须同时做到：

1. 获取当时main的提交SHA，按同一SHA读取完整清单作为基线。
2. 明确本次允许修改的`subject:knowledge_id`集合，只替换这些卡；其他卡所有字段原样保留。
3. 校验候选清单每个字段，检查无其他条目改动、无修订号下降、无旧条目消失，并核对本次资源的字节哈希。可运行项目的`tools/content_contract.py`或`publisher.ps1 check-manifest`，详见协议中的命令；无法运行时实现等价检查，不得声称已经跑过工具。
4. 提交必须基于第1步的提交SHA，使用非强制条件更新；远端已变时重新读、重新合并和检查。不得把旧清单直接挂在新父提交上推送，不得force push。
5. 推送后按实际返回提交SHA再次核对本次卡片及资源，才报告已发布。失败保留待发布差量，不影响教学，不清空手机数据。

本地锁无法保护独立的API发布端。不能确认自己的上传工具支持上述条件更新时，停止覆盖主清单，转交待发布差量给统一发布器。

此次不批量补来源、不统一旧哈希、不改历史ID，不主动修改其他学科卡片，也不把整份学习主模型上传。请确认你后续采用的是统一发布器，还是具备基线条件检查的独立发布路径，并只报告实际执行过的校验。
